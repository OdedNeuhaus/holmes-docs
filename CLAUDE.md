# CLAUDE.md: HolmesGPT Docs

This repo is the internal technical documentation site for our organization's **HolmesGPT** system: the OpenWebUI-based UI, our patches to HolmesGPT, skills/toolsets, Grafana dashboards, deployment, and operations. It is a **Docusaurus 3 site written in Hebrew (RTL)**, built into an nginx image and deployed by ArgoCD.

**Your main job here:** developers hand you raw material (pasted notes, Slack threads, English text, YAML, logs, screenshots, files dropped in `inbox/` or straight into `docs/`). You turn it into polished Hebrew Docusaurus pages in the right place. The developer should not need to know Markdown, Docusaurus, or this repo's conventions. That is your job.

For the step-by-step intake workflow, use the **`/add-docs` skill** (`.claude/skills/add-docs/SKILL.md`). Use it whenever someone wants to add, write up, document, move, or edit content, even if they don't name it. This file is the reference that the workflow relies on.

---

## Non-negotiables

1. **Talk to developers in English.** Questions, updates and summaries in chat are always English, even if the developer writes in Hebrew. Hebrew is only for the docs content itself.
2. **All prose in the docs is in Hebrew.** This includes titles, descriptions, headings, body text, alt text, admonition titles, table headers and Mermaid labels. It applies even when the input is English, which you translate. The one exception: a page about a named component or product is titled with just that name (`title: Open-WebUI`). Code, commands, identifiers, error messages and log lines stay verbatim.
3. **Never invent facts.** Every command, value, version, hostname, path and claim must come from the input or from the repo. If something essential is missing, ask. If a minor detail is missing, **list it in your chat summary. Don't put `:::note[חסר מידע]` boxes on pages**; the developer removes them. When the input gives examples on purpose ("for example, 2 means..."), that is not a gap. Put a note on the page only if the page would actively mislead without it.
4. **Confirm placement before writing.** Ask whether this is a new section (פרק), a new page in an existing section, or an addition to an existing page. Always recommend an option (see the skill). Skip the question only if the user already stated the placement explicitly.
5. **No secrets.** Redact tokens, passwords, keys, kubeconfigs and credentials in text, code and screenshots. `make check` catches common patterns, but you are the first line of defense.
6. **Finish green.** `make check` and `make build` must both pass before you say you're done.
7. **Git:** work on a `docs/<slug>` branch. Commit only when the user agrees, and push or open an MR only when asked.

## How the site is built

| Piece | Details |
|---|---|
| Framework | Docusaurus **3.10** (`@docusaurus/faster`, Rspack), React 19, TypeScript config |
| Layout | Content lives in **`docs/`** at the repo root. The Docusaurus project lives in **`site/`** and reads `../docs` (`docs.path` in `site/docusaurus.config.ts`), so `@site/...` imports resolve to `site/`. Infrastructure lives in **`deploy/`**. |
| Locale | Single locale `he`, `direction: 'rtl'`, `htmlLang: 'he-IL'` (see `site/docusaurus.config.ts`) |
| Markdown | `markdown.format: 'detect'`: **`.md` = plain CommonMark**, **`.mdx` = MDX**. Mermaid enabled. |
| Docs route | `docs/` is served at `/docs`. `docs/intro.mdx` is `/docs` itself (`slug: /`). |
| Sidebar | Fully autogenerated from folder structure (`site/sidebars.ts`). Never hand-edit the sidebar. Anything under `docs/` whose name starts with `_` (e.g. `docs/_templates/`) is excluded from the site. |
| Search | `@easyops-cn/docusaurus-search-local` with `language: ['he', 'en']`. The index is only built by `make build`, so search is empty in `make dev`. |
| Fonts | Self-hosted via `@fontsource-variable` (Heebo, Rubik, JetBrains Mono). The network is air-gapped, so there are no CDNs or Google Fonts. |
| "Last updated by" | Enabled only when the build runs inside a git repo with at least one commit (`IN_GIT` in config). |
| Broken links | `onBrokenLinks: 'throw'` and `onBrokenMarkdownLinks: 'throw'`, so a broken internal link fails the build. |
| Styling | `site/src/css/custom.css` (brand: mint `#56F5CA`, deep teal `#11383A`). Homepage is `site/src/pages/index.tsx`. |
| Runtime | `deploy/Dockerfile` has two stages: `node:22-bookworm` build, then `nginx-unprivileged` on port 8080. The build context is the repo root (`docker build -f deploy/Dockerfile .`), with ignores in `deploy/Dockerfile.dockerignore`. `deploy/nginx.conf` holds the nginx config. |
| Deploy | GitLab CI (`.gitlab-ci.yml`): MR runs check, typecheck and build. `main` builds the image, then commits the new tag to `deploy/helm/holmesgpt-docs/values.yaml` (`[skip ci]`), then ArgoCD syncs. |

### Repo layout

The root is intentionally minimal. Writers only need `docs/` and `inbox/`. Keep it that way: don't add files or folders to the root.

```text
docs/                         ← ALL content lives here
├── intro.mdx                 ← /docs welcome page (section cards)
├── <section>/                ← one folder = one section (פרק)
│   ├── _category_.json       ← {"label": "<Hebrew>", "position": N, "collapsed": true}
│   ├── index.mdx             ← section landing page (lists its pages automatically)
│   ├── <page-slug>.md        ← a page
│   ├── <sub-section>/        ← nested section: same rules, recursively
│   ├── img/                  ← images for this section
│   └── files/                ← downloadable attachments (dashboard JSON, example YAML...)
├── contributing/             ← the human "how to write docs" guide (position 99, always last)
└── _templates/               ← page skeletons: page, patch, skill, dashboard, runbook, decision (not published)
inbox/                        ← raw drop zone; git-ignored except README; never published
site/                         ← Docusaurus project (package.json, node_modules, config, src/, static/)
├── src/data/sections.tsx     ← homepage/intro cards, one per top-level section
├── src/components/           ← SectionGrid (cards), SectionPages (section landing lists)
└── scripts/check-docs.mjs    ← content linter (`make check`)
deploy/                       ← Dockerfile, nginx.conf, Helm chart, ArgoCD Application (leave alone)
Makefile                      ← check / build / dev / stop (uses local npm, else Docker); run from the root
```

## Content model

### A page

- File name: **English, lowercase, kebab-case** (`tool-calling-fix.md`). The file name becomes the URL, so never use Hebrew, spaces or underscores. `make check` enforces this.
- Default to **`.md`**. Use `.mdx` **only** when the page needs `import` or React components (e.g. `<Tabs>`).
- Required frontmatter:

```yaml
---
title: תיקון ל-Tool Calling          # Hebrew, shown as the H1 and in the sidebar
description: משפט אחד שמסביר על מה העמוד.   # Hebrew, used on cards, SEO and search
sidebar_position: 3                   # order within the section; check siblings, don't collide
---
```

  Optional: `sidebar_label` (a shorter sidebar name) and `tags`. Quote values that contain `:` (`title: "החלטה: ..."`).
- **No `#` H1 in the body.** The title comes from frontmatter. Start the body with a 1–2 sentence summary, then `##` sections.

### A new section (פרק)

Create all four pieces:

1. `docs/<slug>/`
2. `docs/<slug>/_category_.json`: `{"label": "<Hebrew label>", "position": <N>, "collapsed": true}`. N is the next free integer below 99, where `contributing` sits. To place a section between existing ones, use a fractional position (`opening` is `0.5`, before `architecture` at `1`) instead of renumbering.
3. `docs/<slug>/index.mdx`: copy an existing section's `index.mdx` and change `title` and `description`. Keep the `SectionPages` import and `<SectionPages />`. Don't repeat the `description` as a sentence in the body.
4. Add an entry to `site/src/data/sections.tsx` using the **same** title and description. For the icon, use SVG child elements from a [Lucide](https://lucide.dev) icon inside `<Icon>`. If you're not certain of an icon's exact paths, reuse one of the existing icons rather than guessing.

A section folder that contains only `index.mdx` collapses into a single sidebar link. It becomes an expandable category once it has a page. This is expected behaviour.

### Section landing pages (`index.mdx`)

An empty section's landing page is just the frontmatter, the placeholder `:::info[הפרק הזה עוד לא נכתב]` and `<SectionPages />`. **When you add the first real page to a section, delete that placeholder admonition.** Don't add a body sentence that repeats the frontmatter `description`; the developer finds it redundant. `<SectionPages />` renders cards for the section's pages automatically, so don't hand-maintain page lists.

A short single-topic section (such as `opening/`, the foreword) keeps its content directly in `index.mdx` instead of an `index.mdx` plus one page.

## Writing in Hebrew

- **Voice:** impersonal present plural, as in the existing guide: "מריצים", "פותחים", "מוסיפים". It is gender-neutral and consistent. Avoid gendered imperatives ("הרץ" or "הריצי"). This is for instructions and runbooks. **Narrative and history pages** (a foreword, "why we chose X", what we changed and why) keep the author's first person ("התחלנו", "אפרט"), tone and slang. Fix typos and drop pure filler only.
- **Tone:** professional, direct, short sentences. Explain **why**, not just what, because this documentation is a handoff to the next maintainers.
- **Technical terms stay in English:** Pod, Deployment, patch, toolset, ArgoCD, OpenWebUI, commit, PR and so on. Attach the Hebrew prefix with a hyphen: "ה-Pod", "ב-ArgoCD", "ל-values.yaml". Don't invent Hebrew translations for established terms.
- **Bidi safety:**
  - Don't start a paragraph, list item or table cell with an English word or code. Lead with Hebrew ("ה-Deployment של Holmes..." instead of "Deployment של Holmes..."). Exceptions: a table cell or list item that is only a product or component name holds just the name (`PostgreSQL`, not `מסד PostgreSQL`), and a sentence may start with a product or proper name **without** a definite "ה-" ("Holmes מגיע עם...", not "ה-Holmes מגיע עם..."). Generic nouns keep it ("ה-Pod", "ה-Chart").
  - Never separate two English words with only a colon or comma ("מול Simple: Holmes"). They display in the wrong order, so put Hebrew between them.
  - Wrap file paths, commands, flags, env vars, resource names, values and placeholders in backticks. Inline code is isolated LTR and keeps the sentence order intact.
  - **No Hebrew inside code.** Hebrew in code blocks renders in a confusing order, so explanations go in the prose above or below the block. See *Code snippets* below.
- **Keep verbatim:** error messages, log lines, CLI output, UI button labels as they appear on screen, and product names. Readers search for these exact strings.
- **Translate** English prose from the input faithfully. Don't summarize away details.

## Formatting reference

### Code snippets

- **No Hebrew in code, ever.** Code, config and comments inside code blocks are English. If the developer's snippet has Hebrew comments, translate them to English, or move the explanation into the Hebrew prose. The only exceptions are rendered content: ```` ```md ````/```` ```mdx ```` examples of doc pages, and Mermaid labels. `make check` warns on anything else.
- **Always tag a language:** `bash`, `yaml`, `json`, `python`, `typescript`, `diff`, `promql`, `ini`, `toml`, `docker`, `nginx`, `sql`, and `text` for logs and output. `make check` warns on untagged fences.
- **Commands and output go in separate blocks.** Commands go in `bash`, with no `$ ` prompts, so they're copy-pasteable. Output goes in a `text` block, optionally with `title="פלט"`.
- Use `title="path/to/file.yaml"` when a snippet is (part of) a real file. Highlight lines with `{2,5-7}` after the language.
- Show patches and config changes as `diff` blocks.
- Trim long output with a `# ...` line, and keep the lines that matter (the error, the key values).
- Use placeholders in `<angle-brackets>` inside code (`kubectl -n <namespace> ...`). **In prose they must be in backticks.** In `.md` a bare `<namespace>` is parsed as an HTML tag and silently disappears. `make check` catches it.
- Redact secrets as `<REDACTED>` inside code.

### Images

- Store them in `docs/<section>/img/` with lowercase kebab-case names prefixed by the page slug: `img/main-dashboard-latency-panel.png`.
- Reference them relatively with Hebrew alt text: `![פאנל ה-latency בדשבורד הראשי](./img/main-dashboard-latency-panel.png)`.
- **Getting the file:**
  - From `inbox/`: move it into place.
  - Pasted into chat: Claude Code shows `[Image: source: /path/...png]`. Copy from that path.
  - If there's no path, ask the user to save it into `inbox/`. Never reference files outside `docs/` or `site/static/`.
- **Look at every image** with Read before publishing. Write accurate alt text, and check for visible secrets, tokens or personal data. If you find any, tell the user and don't publish it as-is.
- Keep images under 1MB. If a screenshot is huge, downscale it (Python/PIL if available) or tell the user. Prefer PNG for screenshots and SVG for diagrams.
- No external image URLs. The site is air-gapped for readers too.

### Diagrams

Use Mermaid in a ```` ```mermaid ```` block for flows, architecture and sequences described in the input. Quote Hebrew labels (`A["שירות ה-UI"] --> B["Holmes API"]`), and prefer `flowchart LR` or `sequenceDiagram`. **Only draw what the input states.** A diagram is a factual claim.

### Admonitions (callouts)

Titles use bracket syntax only: `:::tip[כותרת]`. The old `:::tip כותרת` form renders as raw text and `make check` flags it.

Use them **rarely**. Don't turn the author's statements into callout boxes: a known issue, caveat or opinion written as a sentence stays a plain paragraph. A box is for something truly dangerous (data loss, outage, security) or a real shortcut.

| Type | Use for |
|---|---|
| `:::note` | Background and context |
| `:::tip` | Shortcuts and good practice |
| `:::info` | Neutral important facts |
| `:::warning` | Something that can break or surprise |
| `:::danger` | Data loss, outages, security |

### Other elements

- **Tables** suit structured facts: versions, environments, owners, config keys. Keep each cell short.
- **Links between pages** use relative file paths **with extension**, e.g. `[הפריסה](../deployment/index.mdx)` or `[ה-patch](./tool-calling-fix.md)`. The build verifies these.
- **Anchors:** Hebrew headings produce fragile Hebrew slugs. When you link to a heading, give it an explicit English ID and link to `./page.md#install`. In `.md` the syntax is `## התקנה {#install}`. In `.mdx` it is `## התקנה {/* #install */}`, because `{#install}` is parsed as a JS expression and breaks the build.
- **Attachments** (dashboard JSON, full example configs) go in `docs/<section>/files/` and are linked relatively: `[ה-JSON של הדשבורד](./files/main-dashboard.json)`. Don't paste huge JSON into pages. Summarize it, show the relevant fragment, and link the file.
- **Collapsible content** uses `<details><summary>כותרת</summary> ... </details>`, which works in `.md` as well.
- **Tabs** (`.mdx` only) use `import Tabs from '@theme/Tabs'; import TabItem from '@theme/TabItem';`. See `docs/contributing/index.mdx` for a working example.
- **In `.mdx`**, `{`, `}` and `<` in prose break the build. Put them in backticks or code blocks.

## Validation and preview

```bash
make check   # seconds: naming, frontmatter, admonition syntax, vanishing <tags>, missing images, secrets, raw files
make build   # full production build (runs check first); fails on broken links / MDX errors
make dev     # dev server at http://localhost:3000 with live reload
make stop    # stop the dev server (Docker mode)
```

- The Makefile uses local `npm` if present, otherwise Docker (`node:22-bookworm`). With local npm, `make dev` runs in the foreground, so start it as a **background** command.
- Fix **every error**. Fix warnings unless there's a good reason not to, and tell the user when you leave one.
- When done, give the user the URL of each new or changed page, e.g. `http://localhost:3000/docs/architecture/llm`.
- `node_modules` must match the platform that runs it. If the build fails with `Cannot find native binding` or `@rspack/binding-...`, run `rm -rf site/node_modules` and then `make install`.

Everything under `site/`, `deploy/`, `.gitlab-ci.yml`, `Makefile` and the `.claude/` config is written with **English comments and English tool output**. Hebrew in those files is only for strings that render on the site: navbar and footer labels, the homepage, and the section cards in `site/src/data/sections.tsx`.

## Things not to touch (unless the user explicitly asks)

- `deploy/helm/holmesgpt-docs/values.yaml`, especially the `tag: ... # ci:image-tag` line, which CI owns.
- `deploy/` and `.gitlab-ci.yml`: infrastructure, not content.
- `site/package.json` / `site/package-lock.json`: no new dependencies for content work. The site must build offline from the internal npm mirror.
- `site/docusaurus.config.ts` and `site/src/css/`: only for design or config tasks. Homepage text is in `site/src/pages/index.tsx`.

## Gotchas for design and config tasks

- **rtlcss:** Docusaurus runs rtlcss over *all* CSS for RTL locales. It flips `left`/`right`, `direction`, `translateX`, box-shadow offsets and so on. CSS that must stay physical or LTR (code blocks, the homepage terminal) must be wrapped in `/*rtl:begin:ignore*/ ... /*rtl:end:ignore*/`. Prefer logical properties (`margin-inline-start`), which need no special handling.
- The homepage hero is always dark by design, and the rest of the site follows the light/dark theme.
- The `future.v4` flags require `@docusaurus/faster`. Don't remove it.
